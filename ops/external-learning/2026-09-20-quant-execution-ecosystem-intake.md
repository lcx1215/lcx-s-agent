# 外部调研：GitHub / 社区里"跑着的量化自动交易系统"是怎么做的

- 日期：2026-09-20
- 触发：用户方向 = 自动交易由系统做（量化 / 低频 / 日频），且明确要求"兼容性要高"，
  因为会结合 GitHub / 小红书上别人做的方案。
- 与既有文档的关系：`2026-09-18-trading-agent-ecosystem-intake.md` 只覆盖 **TradingAgents 一家**
  （该文中出现 4 次），**完全没有**执行引擎、国内实盘通道、影子盘/审批、过拟合等主题。
  本文是**补充**，不是重复。
- 证据性质：**公开仓库 README 与公开文章的原文引用**，不是本机验证。凡属本机状态的一律标注。

---

## 一、结论先行

三个可迁移结论，按价值排序：

1. **所有严肃系统都把「信号」与「分配」分开** —— LLM 出判断，**分配是确定性的**。
   这条直接印证了我们对 (A) 执行已声明规则 vs (B) 系统临场决策 的区分。
2. **上线是四级阶梯，不是开关**：影子盘 → 纸面 → **人工审批** → 实盘。
   我们的 `draft → active` 只有两级，缺中间那两级。
3. **国内个人实盘的事实标准是 miniQMT（迅投 QMT）**，这不是"要不要接券商"的抽象问题，
   而是一个具体的、有 API 形态的、可插进现有 `FinanceExecutionAdapter` 的选项。

## 二、三个样本，三种形态

### 样本 A：TradingAgents（分析框架，不执行）

- 定位：**多智能体 LLM 股票分析框架**，模拟交易公司（分析师/研究员/交易员/风控/组合经理）的
  分析、辩论、风控全流程。
- 覆盖：只到**信号层**。原文描述为"让 AI 智能体团队替你开交易公司"。
- **不接券商、不执行。** 风控是"一个会发言的角色"，不是会拦单的门禁。
- 对我们的意义：**它不是一个可参照的执行系统**。若有人拿它当"自动交易系统"，那是误读。

### 样本 B：AI_Trading_Agents（中文，低频，最接近我们的方向）

原文自述：

> "面向股票**低频量化研究、模拟交易、风控评估与运营监控**的多智能体交易系统……结合大语言模型、
> 多数据源、**规则化信号**、组合管理、回测评估、**影子盘**和**人工审批**流程，帮助研究者和开发者
> 搭建**可验证、可复盘、可渐进上线**的 AI 交易实验平台。"

目录结构（这是最有价值的部分 —— 它就是分层）：

```
tradingagents/
├── signals/       # 信号 schema、解析器、fallback provider
├── portfolio/     # 组合模型和【确定性分配器】
├── risk/          # 风控引擎
├── live/          # 实盘/影子盘接口、【审批】、检查、订单服务
├── sim/           # 模拟交易和状态存储
├── backtest/      # 回测、walk-forward、过拟合诊断
└── storage/       # SQLite 与影子盘存储
```

关键设计（原文引用）：

- **结构化信号**："统一输出 `BUY`、`OVERWEIGHT`、`HOLD`、`UNDERWEIGHT`、`SELL` 等信号和置信度"
  ⇒ **LLM 的输出被压成一个窄枚举 + 置信度**，不让它直接输出下单指令。
- **确定性分配器**（`portfolio/` 目录明确写了"确定性"）⇒ **信号是 LLM 的，分配不是**。
- **风控**："仓位约束、行业/个股上限、止盈止损、**回撤熔断**、对冲和再平衡逻辑"。
- **四级阶梯**：shadow run → paper trading → **审批队列** → live。
- **上线清单**（`live/` 里的"检查和上线清单"）⇒ 上线是一个**有检查项的流程**，不是开关。
- 它的自我定位（原文）：
  > "本项目默认更适合研究、模拟交易、影子盘和低频验证，**不建议直接无人值守实盘运行**。"
  > "真实交易前必须加入**人工审批、风险限额、熔断机制和小资金验证**。"

**这条自我定位是对我们最有力的外部印证**：我们识别出的"风险上限不声明即不封顶"这一危险默认值，
在有实际工程经验的同类项目里被明确写成"必须加人工审批与风险限额"。

### 样本 C：Freqtrade（成熟执行引擎，33000+ commits）

- 策略 = **Python 类**（`IStrategy` 接口），放在 `user_data/strategies/` 下由引擎加载。
- 风控与资金管理是**必填配置**：`max_open_trades`（最大并发持仓数）、`stake_amount`（单笔金额）、
  止损、追踪止损、回撤保护。
- `dry_run` 与实盘**同一套策略代码**，靠配置切换。
- 有 `FreqAI` 子模块做自适应模型，有 `hyperopt` 做参数寻优。

对我们的意义：**"策略 = 可插拔代码单元 + 必填的仓位/风控参数"是事实标准**。
我们的 `form` + 必填信封（`instruments` / `emits` / `schedule`）在形状上与此同构；
差别在于我们**没把'不声明即拒绝'写进仓位/金额字段**（见第四节）。

## 三、国内实盘通道：miniQMT（此前我们完全没覆盖的一层）

此前我们只知道"venue 适配器 0 个、需用户给凭据"。调研给出了**具体答案**。

来源：《2026 个人量化实盘终极指南：从回测到全自动交易，miniQMT 全解析》（知乎，2026-06-02）。

| 项               | 事实（原文引用）                                                                                                                                 |
| ---------------- | ------------------------------------------------------------------------------------------------------------------------------------------------ |
| 是什么           | "由迅投科技开发、国内主流券商广泛采用的专业量化交易终端"；QMT = Quick Market Terminal                                                            |
| 为什么用 miniQMT | 原生 QMT "内置的 Python IDE 体验极差，而且对第三方库的支持非常有限……在原生 QMT 里根本无法安装和使用"                                             |
| 怎么开           | "下载并安装券商提供的 QMT 客户端……**勾选右下角的【独立交易】选项**"                                                                              |
| API 形态         | `XtQuant` 库：`xtdata`（行情）+ `xttrader`（下单）。下单 = `xt_trader.order_stock(account, stock_code, order_type, price, quantity, trade_side)` |
| 标的范围         | 股票、ETF、可转债的下单/撤单/改单；融资融券专项接口                                                                                              |
| 运行方式         | **本地运行**（"你的策略代码完全运行在自己的电脑或服务器上"），代码不上传                                                                         |
| 数据质量         | "直接对接券商行情服务器……毫秒级延迟的实时行情推送"                                                                                               |

**对我们系统的直接意义**：

1. `FinanceExecutionAdapter` 的 `kind: "paper" | "venue"` 契约**正好能吃下这个形态** ——
   一个 `venue` 适配器 = 对 `XtQuant` 的薄封装，且源码原话是
   "a venue adapter can replace the paper one **without touching this code**"。
2. **但它只能本地运行**（QMT 客户端必须登录着）⇒ 这与"云端部署"冲突。
   这是**架构约束**，不是缺陷，需要在选路时就知道。
3. 凭据形式 = 资金账号 + 交易密码 + 本地 userdata 路径 ⇒ **必须由用户本人提供，不能代做**
   （与既有判断一致）。

## 四、社区踩过的五个坑（来自一篇三年经验复盘）

来源：《从手工交易到量化：我踩过的5个坑》（知乎，2026-07-18）。按"六步闭环"（数据获取 → 策略开发 →
回测 → 优化 → 仿真 → 实盘）排序：

| #   | 坑                     | 原文教训                                                                                                                                           | 对我们的映射                                                                     |
| --- | ---------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------- |
| 1   | 迷信免费数据不校验     | "某个月份的收盘价全部重复了前一天的数值。策略实际上是'抓住了这个 bug'在赚钱"                                                                       | 我们已有 `finance-source-health` 方向（旁窗在做）；**数据质量校验要有交叉验证**  |
| 2   | **一上来就写代码**     | "**先写规则，再写代码。规则说不清楚，代码一定写不对。**"                                                                                           | **这正是 `finance-strategy-rule-ledger` 存在的理由** —— 外部印证了它是正确的起点 |
| 3   | 回测用全量数据         | "训练集和测试集没分开……夏普 3.0+，第二天开模拟盘一个月亏 15%"                                                                                      | 我们尚无回测/走样验证层                                                          |
| 4   | 只追求收益最大化       | "收益最高的那组参数，往往也是最'脆弱'的……好参数 ≠ 高收益，好参数 = 收益不错 + 回撤可控 + **参数不敏感**"                                           | 与缺口 ③（因子演化环）相关；但**固定规则路线不需要参数寻优**                     |
| 5   | **仿真跑一周就上实盘** | "仿真至少跑 **4 周**，而且这 4 周里**必须经历至少一次不利行情**（震荡、反转、跳空）。只有在不利行情中还能保持纪律、不手动干预，才说明策略准备好了" | **这是一条可编码的上线判据**（见下）                                             |

坑 5 值得单独说：它是唯一一条**能变成机器判据**的。
"跑满 N 天"容易编码，"经历过不利行情"需要定义什么叫不利 —— 但这恰恰是可以声明的：
把"必须覆盖的行情形态"作为规则激活的前置条件写进账本，而不是靠人记着。

## 五、对本系统的具体缺口（本次调研新识别）

| #   | 缺口                       | 依据                                                                                                                                        | 优先级                       |
| --- | -------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------- |
| 1   | **自动模式强制封顶**       | Freqtrade 的 `max_open_trades` / `stake_amount` 是**必填**；AI_Trading_Agents 明写"必须加入风险限额"。我们三字段**全可选 = 不声明即不封顶** | 高（自动化前必须）           |
| 2   | **分配层缺失**             | 三个样本都有"信号 → 分配"的分离；我们只有规则、没有把规则输出变成确定性的下单量                                                             | 高                           |
| 3   | **上线阶梯只有两级**       | 我们是 `draft → active`；样本 B 是 shadow → paper → 审批 → live 四级                                                                        | 中                           |
| 4   | **"经历不利行情"这条判据** | 坑 5。可声明、可编码，且不需要任何新状态根（重放已有回执流即可）                                                                            | 中                           |
| 5   | 回测 / 走样验证层          | 三个样本都有；我们无                                                                                                                        | 低（固定规则路线不那么依赖） |

**不需要做的**：参数寻优 / 因子演化（缺口 ③）。用户走的是固定规则路线，
坑 4 明确说"最脆弱的往往是收益最高那组参数" —— 演化能力对低频固定规则是负担不是优势。

## 六、给 `finance-strategy-rule-ledger` 的形态校验

本次调研也反过来验证了我们昨天的设计选择：

- **开放信封是对的** —— 样本 C 的策略是 Python 类、样本 B 的信号是窄枚举、社区方案形态各异；
  若我们把 `form` 做成枚举，接任何一个都要改 schema + 加迁移。
- **`emits` 字段（orders / signal / target_weights）与样本 B 的分层一致** ——
  样本 B 正是"信号层输出窄枚举、组合层做确定性分配"。
  我们的 `emits` 允许规则声明"我只出信号、不下单"，**这与业界分层的方向一致**。
- **`provenance.origin` 记外部来源** —— 用户明说会结合外部方案，没有出处就无法追溯
  （样本 B 也强调"可验证、可复盘"）。
