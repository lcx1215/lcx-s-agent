# 答案路径门禁：失效模式清单（假阴性 / 假阳性 × 该查的构造）

> 用途：**下一轮审计的检查表**，以及**看哪些格子还没探过**。
> 来源：2026-09-20 会话逐轮实测（编号 ⑥–㉓，共 21 条，明细见 `.workbuddy-ai/memory/2026-09-20.md`）。
> 配套方法论：skill `keyword-gate-pattern-audit`。

## 0. 这份清单为什么存在

这批门禁的契约是"**用正则扫散文，决定答案是否被采纳**"。这类实现**必然**有两个方向的误差：

- **假阴性（FN）**：该拦的没拦。**没有症状**——答案只是被静默认证。所以它只能靠**主动构造**发现。
- **假阳性（FP）**：不该拦的拦了。有症状（好答案被替换），但容易被当成"门禁很严"而接受。

⇒ 因此清单按**方向**分两张表，而不是按文件分。每条都给出**退化匹配**（错在哪）与**应查的构造**（改法）。

### 1c. 第三个子形态：**契约声称"全部"，但没有校验"全部"**

| ID   | 子形态                                                   | 说明                                                                                                                                                                                                                             |
| ---- | -------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| F-22 | **声明式门禁只校验被声明的东西，不校验声明是否覆盖全部** | `finance-answer-grounding-gate.ts` 是**走在"改表示"正确路上**的模块（明确放弃"从词推断含义"，改成模型在 ` ```figures ` 块里声明每个数字的 kind，门禁只做机械比对）。但它**只比对声明**：正文写了什么、是否都被声明过，从不检查。 |

F-22 实测（snapshot 里只有 212.44）：

| 用例                                       | 修前                      | 修后                       |
| ------------------------------------------ | ------------------------- | -------------------------- |
| 正文写 **999.01**，声明块只声明 212.44     | **verified** ← 编造值通过 | `undeclared_figures`       |
| 正文两个数字，声明块只声明其中一个         | **verified**              | `undeclared_figures`       |
| 两个 figures 块（第二个声明编造的 999.01） | **verified** ← 只读第一块 | `not_verifiable`           |
| 声明块空数组                               | `not_verifiable` ✓        | 不变（fail-closed 已生效） |
| 声明 999.01（不在 snapshot）               | `ungrounded` ✓            | 不变（优先级更高）         |

⇒ **"没有声明块"是 fail-closed 的，但"少声明"是盲的** —— 而"少声明"正是模型想写一个它没拿到的数字时会采取的形状。
**判据：门禁说"必须声明每一个"时，去问"那谁校验'每一个'？"**

修法（机械的，不需要理解散文）：从正文里取出**像数值**的数字（带单位 / 带小数 / 带千分位），
排除声明块本身、日期、指数名、期限标签、期数，再要求每个都匹配某条声明。
新增 verdict `undeclared_figures`；消费方是 `verdict !== "verified"` ⇒ **自动 fail-closed**。
**两条"别剥过头"的守卫**（已用测试钉住）：`1,309.22` 的逗号必须**夹在数字之间**（否则
"Step 1 of 3, as of…" 里的 `3,` 会被当成千分位）；科学计数法 `1.0e-11` 要整体取到（否则只取 `1.0`）。
并加 `askText` 豁免——**读者自己给的数字不是答案在编造**（同 F-17）。

### 1d. 执行缝（`intent-compiler` 3 条 + `execution-adapter` 2 条）："检查了一个轴、漏了另一个" / "只校验了控制、没校验喂它的输入"

**为什么单独列**：这三处错了**是钱的问题**，比答案路径的同类问题后果高一个量级。
而且它们不属于前面任何一个 ID —— 形状是**"退化情形只处理了一半"**。

| ID   | 形状                               | 实测（ref=100，class A=结构止损 1%）                                                                                                                                                                                                                                                                                                                                                                          |
| ---- | ---------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| F-23 | **只校验了"零距离"，没校验"符号"** | 做多 + 止损在上方 **110**（已被击穿）⇒ **编译通过**，按 `distance=10` 算出 `qty=100`，note 写"sized from stop distance 10"；做空 + 止损在下方 90 同理。**`Math.abs` 把符号抹掉了**，而 `distance === 0` 那条守卫说明作者确实想到了退化情形 —— 只是只想到一个轴。                                                                                                                                              |
| F-24 | **类型声明了用途，但没有实现**     | `targetPrice` 的类型注释写 "used only to check reward against risk"，`finance-research-conclusion-prompt.ts` 还专门让模型产出它，`finance-conclusion-intake.ts` 解析并透传 —— **全仓没有一处读它**。目标价比止损还近、甚至方向反了，都编译通过。⇒ **读者（和模型）以为盈亏比被校验过。**                                                                                                                      |
| F-25 | **两个字段互相矛盾**               | 非结构止损的类别（C 类 thesis 止损）若同时给了 `invalidationCondition` 与 `invalidationPrice`，会**编译通过并带出 `stopPrice`**，而 note 同时写着 "sized on full position at risk (**no price stop**)"。数量按"全仓在险"算 ⇒ 实际风险只有 3% 预算的约 **1/20**。模块自己的测试（"leaves the stop off when the class uses a condition instead of a price"）已声明了正确意图 ⇒ **这是违反自身意图的可达路径**。 |

**修法**（都按"拒猜"的模块哲学）：

- F-23：显式校验止损在**正确一侧**（做多须低于、做空须高于），否则拒。零距离那条守卫保留原样（顺序上先判符号、再判零）。
- F-24：目标价**只做一致性校验**（在错误一侧就拒），并**把类型注释改成实情**：
  "Checked only for coherence… No reward/risk ratio floor is enforced"。
  **故意不设盈亏比下限** —— 那是策略判断，在这里发明一个等于"把猜测洗成受强制的决策"，
  与 `classifyFinanceStrategy` 拒绝猜类别是同一个理由。
- F-25：`stopPrice` **只对结构止损类别**带出；非结构类别若被给了价格，**用一条 note 明说"它没有被当作止损携带"**（避免静默丢弃）。

**判据（可复用）**：**"退化情形我只处理了哪一个轴？"** —— 零、负、相等、方向反了、量级异常，是**五个不同的轴**，
处理其中一个不代表处理了其余。以及：**类型/注释承诺的行为，去 grep 一次它的实现**（F-24）。

**验证**：`finance-intent-compiler.test.ts` 15 → **22**；**3 次变异各自精确对位**
（退止损方向 ⇒ 2 红；退目标方向 ⇒ 1 红；退"仅结构类别带 stopPrice" ⇒ 1 红）；还原字节一致（`ea14d30e…`）。

| ---- | ------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |

**新判据（可复用）**：**"这个字段/参数在别处是什么语义？"** ——
F-32 是同一字段两处相反（契约 fail-closed、实现 fail-open），**只有把两处放在一起读才发现**。

**同一个缝的下一层：`finance-execution-adapter.ts`（`placeFinanceOrder`）**
这一层是**放行订单的最后一道边界**，而且 `placeFinanceOrder` 是导出 API、收普通对象 ⇒
**不经过 `compileExecutionIntent` 也能到达**。它有 32 个正则、6 张常量表、3 个拒绝码，检查很密 ——
但仍然漏了两处：

| ID   | 形状                                         | 实测（ref=100，做多，上限 1000 / 本单 500）                                                                                                                                                                                                                                                                                                                                                                                                                                                     |
| ---- | -------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| F-26 | **"最后一道边界"从不读 `stopPrice`**         | 止损 **120**（已击穿）/ **100**（等于现价）/ **0** / **NaN** ⇒ **四个全部下单成功**。而 intent 类型的注释自己写着"按止损距离定量、却下一个不带止损的单，比不要止损更糟，因为它**看起来受控**"。**它校验了 `limitPrice` 的存在与缺失，却完全没读 `stopPrice`。**                                                                                                                                                                                                                                 |
| F-27 | **上限的计数器没校验，负数把控制变成空操作** | `committedInstrumentNotional: 900` ⇒ 拒绝 `risk_budget_instrument_notional_exceeded`；**`-1e9` ⇒ 下单**。`ordersPlacedThisRun: 1` ⇒ 拒绝 `risk_budget_order_count_exceeded`；**`-100` ⇒ 下单**。上限本身有 `isPositiveFinite` 守卫（所以"缺省的上限不施加约束"是有意的），但**喂它的两个计数器一个都没守** ⇒ 负数**放宽**了它本该消耗的上限，与模块自己写的"the narrowing path is never a widening"直接矛盾。计数器由调用方给 ⇒ **一个有 bug 的计数器（未初始化、或由减法得出）就是现实路径**。 |

**修法**：F-26 ⇒ `stopPrice` 存在时必须为正有限，且必须在入场价的**正确一侧**（做多须低于、做空须高于），
两个独立拒绝码（`execution_intent_stop_price_must_be_positive` / `..._on_wrong_side`）。
F-27 ⇒ 两个计数器必须为**非负有限**，各自一个拒绝码。**不加默认值** —— 模块自己的哲学是"缺省的上限不施加约束"，
所以这里也只能拒绝一个负值，不能替它猜一个 0。

**验证**：`finance-execution-adapter.test.ts` 19 → **26**；**3 次变异各自精确对位**
（退整个止损块 ⇒ 3 红；退"必须为正"那一支 ⇒ 1 红；退已用额度计数器的校验 ⇒ 1 红）；还原字节一致（`81f983ef…`）。

**新判据（可复用）**：**"这个控制的输入，和这个控制本身，哪一侧被校验了？"** ——
F-27 是典型的"控制被守住了、喂它的数没被守"。凡是形如 `if (cap && counter + x > cap)` 的写法，
都要问一句 `counter` 从哪来、谁保证它是非负的。

### 1f. 第五个子形态：**退化配置制造了一个不该有的结果**

**形状**：函数把调用方传的可调参数直接拿去做算术/比较，**不校验它们是否落在有意义的范围内**。
于是一个退化值不是"报错"，而是**产出一个看起来很正常的结论**。这与 §1b 的"上游谓词漏一类"
不同：谓词漏是"检查不跑"，这里是"检查跑了，但被喂了荒谬的输入"。

同一形状在本轮**四处各有一份**（正是 F-01/F-02 的"同一语义多层复制"在信号层的重演）：

| ID    | 位置                            | 实测                                                                                                                                                                                                                                                                                                                                                     |
| ----- | ------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| F-30a | `finance-fundamental-signal.ts` | `fullCredibilityCount: -10` + 100 位分析师 ⇒ **`confidence = -2.025`**（负权重）；`deadbandFraction: -0.03` + 目标价**低于**现价 2% ⇒ **`buy`**（两个比较同时成立，第一个分支赢）；`maxConfidence: 5` ⇒ 权重 5。                                                                                                                                         |

## 4. 用法（怎么当检查表用）

**执行缝额外两步**（§1d 的三条都出自这里）：

1. **列出每个退化轴**：零 / 负 / 相等 / **方向反了** / 量级异常。逐轴问"我处理了吗"。
   F-23 就是"处理了零、漏了方向"。
2. **对每个"声明了用途"的字段 grep 一次它的实现**。F-24 的 `targetPrice` 被 prompt 要求产出、
   被 intake 解析透传、被类型注释承诺校验 —— 而全仓没有一处读它。

对**任何**门禁函数，按顺序问：

1. **先读 return-early 条件**（F-13）。谓词不认的输入，后面全部白做。
2. **列出它的每个子条件的最小触发词**（F-07）。逐个问"这个词含该含义吗"。
3. **把字段的真实含义抽掉、只留那个词**（F-15 自检）。
4. **问"这一侧为空时该不该判失败"**（F-18）。
5. **按类别清单逐类核词表**，不要按同义词补（F-02/F-03）。
6. **同一句中英两版各跑一次**（F-14）。
7. **改完必须跑**：组件自带 fuzzer + 场景套件 + **自一致性**（见 §5）。
8. **变异对位**：改坏被测点 ⇒ 红的**必须正好等于**新增用例；还原核对字节哈希。

## 5. 三条"必须做"的护栏（本会话最强的三个抓手）

> 追加一条（F-22 之后）：**门禁说"必须声明每一个"时，去问"那谁校验'每一个'？"**
> 声明式门禁（判结构不判散文）方向是对的，但**覆盖义务本身也要被校验**，否则它只是把"看不见的编造"
> 从散文挪到了声明块的缝隙里。

1. **自一致性属性**——门禁产出的**替换答案必须能再通过门禁本身**：
   ```js
   const d = applyGate({ ask, answer: badAnswer }); // 期望 status=replaced
   expect(findFailures({ ask, answerText: d.text })).toEqual([]); // 替换文本必须干净
   ```
   同时抓两类错：替换文本自己不达标；收紧过头让该被替换的答案变成"被采纳"（`status` 断言先红）。
   **中英两条渲染分支都要测。** 实测它**暴露了下游硬编码**（渲染器写死 `NVDA 成本区间`）。
2. **外部预言机必跑**——组件自带 fuzzer / 场景套件。实测 fuzzer 抓到过我自己收紧过头的正向用例。
   ⇒ **收紧任何"完整性"检查前，先把该组件正向用例的原文读一遍。**
3. **探针隔离**——① 上游谓词不认输入 ⇒ 门禁没跑却显示"未标记" ⇒ **假阴性伪装成"假阳性已修好"**；
   ② 同一门禁多条检查**互相掩盖**。⇒ 每个探针都要带**已知会被标记的对照**，并换掉会触发无关检查的输入。

## 8. 这份清单自己的保鲜期

被问过"它还有用吗"。诚实的回答分两半。

**会腐化的（每次用前先核）**：

- **计数**：§1/§2 的条数、§3 的格子数 —— 只要新增一条就失准。本文因此把计数写成"表内 N + 子形态 M"，
  改的时候要一起改。
- **§6b 的普查数字**：文件数、行数、正则数、常量表数都是某一刻的快照（已加警示）。
- **模块名与函数名**：`finance-*` 层正被其他窗口重命名/拆分。
- **行号**：本文**故意不写行号**（只写文件 + 函数名），因为行号是腐化最快的一栏。

**不会腐化的（这才是它的价值所在）**：

- **"该查的构造"那一栏**：它说的是**怎么把语义要求变成可检查的构造**，与哪个模块无关。
  例："动作动词必须绑标的或数量"、"这一侧为空时该不该判失败"、"值 vs 名字/标签"、"退化轴逐轴核"。
- **"探针问句"那一栏**：每条都是可执行的提问，换一个代码库仍然成立。
- **§4 的步骤 + §5 的护栏**：这是方法，不是结论。
- **§3 的 U 清单**：它是**待办队列**，不是结论 —— 做完一条就划掉并指向落点（U-10a → §1d 是先例）。

**怎么让它保持有用**（三条）：

1. **只往两个地方写**：新构造进"构造"栏、新格子进 U 栏。**叙述进当天的 `YYYY-MM-DD.md`** ——
   本文已 12.9k 字符，开始偏长，继续堆叙述会把它从"检查表"变成"报告"。
2. **做完一条就把 U 划掉并指向落点**，别删 —— 划掉本身是"已探过"的证据。
3. **每次动它先核计数**。

**它替代不了什么**：它不是"已穷尽"的证明，是"已探 + 明确列出未探"的账本。
只要契约仍是"正则/关键词判散文"，§0 的两个方向就都还有格子 —— 这也是它必须一直更新的原因。
